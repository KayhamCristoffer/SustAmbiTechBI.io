Sobre o Projeto

SustAmbiTech BI

Plataforma de inteligência de dados para o ecossistema de mobilidade elétrica brasileiro — evolução do projeto original com nova equipe e novas ambições.

História do Projeto
O SustAmbiTech BI é uma continuação e melhoria significativa do projeto anterior SustAmbiTech (repositório KayhamCristoffer/SustAmbiTech), que estabeleceu os fundamentos da plataforma de análise de mobilidade elétrica brasileira.

A nova versão reescreve a arquitetura de dados, migra para MySQL 8, incorpora fontes oficiais da ABVE e do Carregados.com.br e traz dashboards Power BI embed para visualização direta no portal. A equipe foi renovada — mantendo o Tech Lead original Kayham Cristoffer — e expandida com especialistas em BI, banco de dados, desenvolvimento full stack e sustentabilidade ESG.
v3.0 — 2026 Continuação do SustAmbiTech Nova Equipe MySQL 8 · Power BI · GitHub Pages
Objetivo & Critérios
Consolidar dados públicos sobre veículos elétricos no Brasil em uma única plataforma acessível, com dashboards interativos, mapa de estações em tempo real e análises comparativas por estado, categoria e fabricante.

Critérios: fontes confiáveis (ABVE, Carregados), atualização periódica, dados 100% gratuitos e abertos, visualização responsiva em qualquer dispositivo.

Metodologia & Pesquisa e Desenvolvimento
Os dados são coletados de APIs públicas (Carregados.com.br) e painéis oficiais (ABVE), processados e armazenados em snapshots periódicos no schema MySQL sustambitech. As tabelas BI (BI_EmplacamentosNacionais, BI_ModelosTop, etc.) alimentam os dashboards Power BI via conexão direta ao banco.
API REST Snapshots Mensais Power BI Embed
Abordagem
Optamos por uma abordagem Data-as-a-Service — nenhum dado é armazenado no front-end. O GitHub Pages serve o portal estático; todos os dados ao vivo vêm de fontes terceiras confiáveis (Power BI embed, Carregados iframe) sem dependência de backend próprio, garantindo disponibilidade 24/7 a custo zero.
Processo de Desenvolvimento
1
Pesquisa de Fontes — Identificação e validação de APIs públicas: Carregados.com.br, ABVE BI Frotas/Geral/MHEV.
2
Modelagem de Dados — Criação do schema MySQL 8 com tabelas lookup, transacionais, BI e LogAuditoria centralizado.
3
Integração Power BI — Conexão das fontes ao Power BI com dashboards embarcados diretamente no portal.
4
Portal GitHub Pages — Desenvolvimento do front-end estático com mapa Carregados embed e navegação por abas.
5
Revisão Contínua — Atualização mensal dos snapshots BI e melhorias iterativas no portal com a nova equipe.

Queries & Procedures (SQL)

Queries otimizadas para uso com banco SQL local. Copie e use no MySQL, SQLite ou D1. 

-- ============================================================
-- SCHEMA SUSTAMBITECH — estações de recarga
-- Compatível com MySQL 8, SQLite e Cloudflare D1
-- ============================================================

CREATE TABLE IF NOT EXISTS estacoes (
  id              TEXT PRIMARY KEY,
  nome            TEXT NOT NULL,
  endereco        TEXT,
  cidade          TEXT NOT NULL,
  estado          CHAR(2) NOT NULL,
  cep             TEXT,
  lat             REAL,
  lng             REAL,
  tipos_conector  TEXT,          -- JSON array serializado
  potencia_kw     REAL DEFAULT 0,
  status          TEXT DEFAULT 'Operacional',
  acesso          TEXT DEFAULT 'Público',
  operadora       TEXT,
  fonte           TEXT DEFAULT 'SustAmbiTech',
  data_criacao    TEXT DEFAULT (datetime('now')),
  data_atualizacao TEXT DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS usuarios_admin (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  nome            TEXT NOT NULL,
  email           TEXT UNIQUE NOT NULL,
  senha_hash      TEXT NOT NULL,
  nivel           TEXT DEFAULT 'viewer',
  status          TEXT DEFAULT 'pendente',    -- pendente | ativo | inativo
  token_convite   TEXT,
  token_reset     TEXT,
  token_exp       INTEGER,
  criado_por      TEXT,
  criado_em       TEXT DEFAULT (datetime('now')),
  ultimo_acesso   TEXT
);

CREATE INDEX IF NOT EXISTS idx_estacoes_estado  ON estacoes(estado);
CREATE INDEX IF NOT EXISTS idx_estacoes_status  ON estacoes(status);
CREATE INDEX IF NOT EXISTS idx_estacoes_lat_lng ON estacoes(lat, lng);
CREATE UNIQUE INDEX IF NOT EXISTS idx_admin_email ON usuarios_admin(email);
-- ============================================================
-- STORED PROCEDURES / CTE HELPERS
-- (SQLite usa WITH; MySQL usa DELIMITER $$)
-- ============================================================

-- PROC 1: upsert de estação (insert ou update por id)
-- Uso: CALL upsert_estacao(id, nome, cidade, estado, ...)
INSERT INTO estacoes (id, nome, cidade, estado, lat, lng, status, operadora, data_atualizacao)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, datetime('now'))
ON CONFLICT(id) DO UPDATE SET
  nome = excluded.nome,
  cidade = excluded.cidade,
  lat = excluded.lat,
  lng = excluded.lng,
  status = excluded.status,
  operadora = excluded.operadora,
  data_atualizacao = excluded.data_atualizacao;

-- PROC 2: estações próximas (por raio em graus ≈ km)
-- 0.009 graus ≈ 1 km
WITH nearby AS (
  SELECT *, 
    ((lat - ?) * (lat - ?) + (lng - ?) * (lng - ?)) AS dist_sq
  FROM estacoes
  WHERE lat BETWEEN ? - 0.5 AND ? + 0.5
    AND lng BETWEEN ? - 0.5 AND ? + 0.5
    AND status = 'Operacional'
)
SELECT id, nome, cidade, estado, lat, lng, tipos_conector, potencia_kw, operadora,
       SQRT(dist_sq) * 111 AS dist_km
FROM nearby
ORDER BY dist_sq ASC
LIMIT 20;

-- PROC 3: resumo por estado
SELECT estado,
       COUNT(*) AS total,
       SUM(CASE WHEN status='Operacional' THEN 1 ELSE 0 END) AS operacionais,
       ROUND(AVG(potencia_kw),1) AS media_kw,
       COUNT(DISTINCT operadora) AS operadoras
FROM estacoes
GROUP BY estado
ORDER BY total DESC;

-- PROC 4: inserir usuário admin com hash de senha (base64 simulado)
INSERT INTO usuarios_admin (nome, email, senha_hash, nivel, status, token_convite, criado_por)
VALUES (?, ?, ?, ?, 'pendente', ?, ?);
-- ============================================================
-- VIEWS PARA RELATÓRIOS
-- ============================================================

-- VIEW: mapa_operacionais — somente postos ativos com coords
CREATE VIEW IF NOT EXISTS mapa_operacionais AS
  SELECT id, nome, cidade, estado, lat, lng,
         tipos_conector, potencia_kw, operadora, acesso
  FROM estacoes
  WHERE status = 'Operacional'
    AND lat IS NOT NULL AND lng IS NOT NULL;

-- VIEW: ranking_estados — ranking por número de estações
CREATE VIEW IF NOT EXISTS ranking_estados AS
  SELECT estado,
         COUNT(*) AS total,
         SUM(CASE WHEN acesso = 'Público' THEN 1 ELSE 0 END) AS publicas,
         ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM estacoes), 2) AS pct_total
  FROM estacoes
  GROUP BY estado
  ORDER BY total DESC;

-- VIEW: dashboard_resumo — KPIs para o dashboard
CREATE VIEW IF NOT EXISTS dashboard_resumo AS
  SELECT
    (SELECT COUNT(*) FROM estacoes) AS total_estacoes,
    (SELECT COUNT(*) FROM estacoes WHERE status='Operacional') AS operacionais,
    (SELECT COUNT(DISTINCT estado) FROM estacoes) AS estados_cobertos,
    (SELECT COUNT(DISTINCT operadora) FROM estacoes) AS operadoras,
    (SELECT AVG(potencia_kw) FROM estacoes WHERE potencia_kw > 0) AS media_kw,
    (SELECT MAX(data_atualizacao) FROM estacoes) AS ultima_atualizacao;
-- ============================================================
-- QUERIES DE CONSULTA FREQUENTES
-- ============================================================

-- Q1: Top 10 operadoras por número de estações
SELECT operadora, COUNT(*) AS total,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM estacoes), 1) AS pct
FROM estacoes
GROUP BY operadora ORDER BY total DESC LIMIT 10;

-- Q2: Distribuição por tipo de conector
SELECT tipos_conector, COUNT(*) AS total
FROM estacoes
GROUP BY tipos_conector ORDER BY total DESC;

-- Q3: Estações por potência (DC fast > 50kW)
SELECT id, nome, cidade, estado, potencia_kw, operadora
FROM estacoes WHERE potencia_kw >= 50
ORDER BY potencia_kw DESC LIMIT 50;

-- Q4: Estações em manutenção ou fechadas
SELECT id, nome, cidade, estado, status, data_atualizacao
FROM estacoes WHERE status != 'Operacional'
ORDER BY data_atualizacao DESC;

-- Q5: Verificar autenticidade do usuário (login)
SELECT id, nome, email, nivel, status, ultimo_acesso
FROM usuarios_admin
WHERE email = ? AND senha_hash = ? AND status = 'ativo'
LIMIT 1;

-- Q6: Atualizar último acesso
UPDATE usuarios_admin SET ultimo_acesso = datetime('now') WHERE id = ?;

-- Q7: Busca full-text por cidade/nome
SELECT * FROM estacoes
WHERE nome LIKE ? OR cidade LIKE ? OR endereco LIKE ?
ORDER BY cidade, nome LIMIT 100;
Tutorial: scraper_carregados.py

Script Python puro (sem dependências externas) que coleta dados de estações de recarga com delays anti-bot aleatórios. Roda localmente ou via GitHub Actions toda segunda-feira.

Pré-requisitos
  • Python 3.8+ instalado — python3 --version
  • Conexão com internet (para APIs externas)
  • Repositório clonado localmente — git clone https://github.com/KayhamCristoffer/SustAmbiTechBI.io
  • Nenhuma instalação de pacote necessária — usa apenas stdlib Python
1 Executar o scraper localmente
# Entrar na pasta do projeto
cd SustAmbiTechBI.io

# Executar scraper (modo padrão — delay entre 2–8s por request)
python3 scripts/scraper_carregados.py

# Com delay customizado em segundos (mín. 1s, máx. 30s)
python3 scripts/scraper_carregados.py --delay-min 3 --delay-max 12

# Modo silencioso (menos logs no terminal)
python3 scripts/scraper_carregados.py --quiet

# Forçar modo mock (sem chamadas de rede — para testes offline)
python3 scripts/scraper_carregados.py --mock
2 O que o scraper faz (fluxo detalhado)
Tier 1 — API Carregados
Tenta endpoints carregados.com.br/api/. Respeita rate limits com delay aleatório. Se 401/403/404 → avança para Tier 2.
Tier 2 — OpenChargeMap
API pública api.openchargemap.io. Mais estável. Adicione sua chave em OCM_API_KEY no ambiente para aumentar limite.
Tier 3 — Dataset Mock
Garante que data/estacoes.json nunca fica vazio. Gera 400 estações distribuídas por todos os estados.
3 Sistema anti-bot: delays e headers

O scraper simula comportamento humano para evitar bloqueios por rate limiting ou detecção de bot: 

# Delays aleatórios por tipo de operação:
#   Entre requests de página:    2 – 8 segundos   (padrão)
#   Entre chamadas de API:       1 – 4 segundos
#   Após erro 429 (rate limit):  30 – 60 segundos (backoff automático)
#   Entre lotes de 50 registros: 5 – 15 segundos

# Headers realistas enviados em toda requisição:
#   User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36
#   Accept-Language: pt-BR,pt;q=0.9,en-US;q=0.8
#   Referer: https://carregados.com.br/
#   Accept-Encoding: gzip, deflate, br

# Rotação automática de User-Agent entre 5 perfis diferentes

5 Automação via GitHub Actions

O arquivo .github/workflows/scraper.yml já está configurado. Para ativá-lo:

  1. Acesse github.com/KayhamCristoffer/SustAmbiTechBI.io
  2. Clique em Add file → Create new file
  3. Nome do arquivo: .github/workflows/scraper.yml
  4. Cole o conteúdo do arquivo local (já criado no projeto)
  5. Commit direto na branch main
  6. O workflow rodará toda segunda-feira às 06h UTC automaticamente
  7. Para rodar manualmente: aba Actions → Scraper Estações de Recarga → Run workflow
Opcional: chave OpenChargeMap para dados reais

Sem chave, o Tier 2 usa o endpoint público (limite baixo). Com chave, obtém dados reais de +3.000 estações no Brasil:
